# 技术方案文档

两种模式，看用户要什么：

| 用户说                          | 模式     | 去读                          |
|---------------------------------|----------|-------------------------------|
| 写一份 / 起草 / 新建方案        | **起草** | 本文 §1 → §2 → 写完走 §4 自检 |
| 帮我看看 / review / 优化 / 精简 | **审阅** | 直接走 §4，按严重度输出       |

## 1. 骨架

用 `assets/template.md`。章节顺序是固定的，因为它对应评审时的提问顺序： **为什么做 → 整体长什么样 → 怎么实现 → 怎么验证 →
谁做多久**。

```
扉页     版本/日期/状态/Owner/对应PRD/Milestone
1 背景与范围    为什么做 · 本期范围 · 非本期范围 · 相关链接
2 整体架构      架构图 · 方案选型（对比表 → 结论 → 理由）
3 详细设计      按模块分节，负责人写在节标题上
  3.x 关键技术缺口   已知但没解的问题，集中摆出来
4 接口与数据变更  给调用方和 DBA 的契约面（无变更时整节删掉）
5 测试验收      项 | 判据 | 怎么验
6 排期          模块 | 负责人 | 范围 | 依赖关系
7 后续规划
8 评审意见      留空表，评审后人工填
9 附录          完整配置、脚本、查询语句
```

三条结构上的讲究：

- **负责人写在节标题上**（`3.1 SDK 设计 张三`）。评审时第一个问题永远是「这块谁负责」，写在标题上就不用问。
- **「非本期范围」必须单独成节且写理由**。评审最常见的争议是「为什么不做 X」，提前写掉。
- **完整配置、脚本、长查询语句一律进附录**。正文留「三条设计要点 + 指向附录」。正文是给决策者看的，附录是给实施者看的，混在一起两边都难读。
- **「关键技术缺口」要集中成一节**，别让未决问题散在正文各处。每条写：问题 → 证据 → 可选方案 → **你的建议**。评审是来拍板的，给选项不给建议等于把题甩回去。并标出哪条会**卡住**其他工作——那条要最先定。

## 2. 表述方式

这是本 skill 的核心。技术方案写不好，九成是表述问题而不是内容问题。

需要完整的改写对照（四个真实案例的前后对比）时，读 `references/examples.md`。

### 结论先行

每一节第一句话就是结论，不要铺垫。

```
✗ 在调研了多种方案之后，我们认为从长期维护成本的角度考虑，
   自建方案可能会带来较大的运维负担，因此倾向于选择托管方案。
✓ 采用方案一（上报 GCP）。核心原因是人力不够。
```

### 能用表就不用段落

并列关系一律表格。常见的四种：

| 关系     | 表头                       |
|----------|----------------------------|
| 现状问题 | 诉求 \| 今天的状况         |
| 方案对比 | 对比项 \| 方案一 \| 方案二 |
| 结论理由 | 理由 \| 说明               |
| 验收     | 项 \| 判据 \| 怎么验       |

段落适合写因果和取舍，表格适合写并列和对照。把并列关系写成段落，读者要自己在脑子里建表。

### 一句话一个事实

```
✗ 由于集群是 kubeadm 自建的，没有 Workload Identity，而且 GCP 文档也
   明确要求非 GKE 必须显式提供凭据，所以我们采用服务账号密钥的方式。
✓ 集群是 kubeadm 自建，没有 Workload Identity。
   GCP 文档要求非 GKE 必须显式提供凭据。
   所以用服务账号密钥。
```

### 删掉铺垫词

「值得注意的是」「需要说明的是」「众所周知」「从某种意义上说」—— 这些词后面跟的才是正文，直接说。

### 数字和出处要具体

```
✗ 成本不高              ✓ 一期约 $3~$5/月，算法见 §3.4
✗ 官方文档说要配凭据    ✓ 非 GKE 必须显式给凭据（setup-unmanaged 文档）
✗ 有一些服务没接入      ✓ 九个项目中七个未接入
```

没核实过的，明确标「未验证」「推测」，不要用确定语气混过去。评审时被问到出处答不上来，整份文档的可信度都会掉。

## 3. 什么时候用图

**判断标准是「读者要不要在脑子里建模型」。** 要，就画图。

| 情况                         | 用什么                           |
|------------------------------|----------------------------------|
| 数据流经 3 个以上组件        | **流程图**（箭头 + 组件框）      |
| 同一个东西在不同阶段形态不同 | **分阶段图**，每阶段标出形态变化 |
| 多条并行的线有依赖           | **依赖图**，标出串行点           |
| 分类超过 3 组                | **分组树**                       |
| 两个东西对比                 | 表格，不要画图                   |
| 线性的 2–3 步                | 编号列表，不要画图               |

用 ASCII 图，因为它在 markdown、PDF、飞书、终端里都能看。关键是 **在图上标注**，不要画完再用文字解释一遍：

```
① 应用进程内
   slog.InfoContext(ctx, …) → 写成 JSON 的【字符串字段】
   {"trace_id":"d9eaee3d…"}   ← 此刻只是普通字符串
        ↓ stdout
② 节点磁盘  /var/log/pods/<ns>_<pod>_<uid>/<容器>/0.log
   2026-10-12T05:47:34Z stdout F {"trace_id":"d9eaee3d…"}
   └──── CRI 前缀 ────┘
        ↓ Agent 解析
③ json_parser 的 trace 块
   把字符串【解析进 LogRecord 的原生字段】
   LogRecord.TraceID = [0xd9,0xea,…]   ← 二进制原生字段
   ⚠ 此刻两份并存：attributes 里的字符串 + 原生字段
```

这张图说清了「同一个 trace_id 变了三次形态」——换成文字要写三段，而且读者读完还是会混。

## 4. 自检清单

起草完和审阅时都走一遍。按严重度分三档， **先报 P0**。

### P0 · 事实错误，会误导实施

- **同一事实两处写法不一致。** 典型：§3 的字段映射表写 `logging.googleapis.com/trace`，§8 的查询示例写 `trace=`。读者按哪个做都可能错。
- **口径不一致。** 范围说「三个服务」，费用按「五个服务」算；范围说「四套环境」，费用按「一个集群」算。
- **配置依赖的前提被删掉。** 配置里 `exclude: [/var/log/pods/observability_*/…]` 依赖部署在 `observability` 命名空间，但落位表里没写
  namespace。实施时部署到别的 ns，规则静默失效。
  → 凡是配置里出现的名字（namespace、Secret 名、路径、端口），正文必须有一处交代它从哪来。

### P1 · 前后不一致，会让读者困惑

- **数量词与实际不符。** 标题写「六个字段」，表里 8 行；写「两个硬坑」，列了 3 条。
- **指代失效。** 删掉 A/B/C 编号后，正文还在写「必须等 C 放行」。
- **交叉引用指向不存在的章节。** 删节或改编号后没全文更新。
- **同一概念两种叫法。** 前面叫「Gateway」，后面叫「网关组件」。

### P2 · 影响评审效果

- **验收判据用的不是真实对象。** 一期要接的是 A/B/C 三个业务服务，判据却写着样板工程的 `demo_http_requests_total` 和
  `/api/demo?fail=1` —— 验收通过也不代表目标服务真的接上了。
- **只剩一句话的空壳章节。** 要么补内容，要么删掉。
- **正文和附录重复。** 同一张表两处都有。
- **缺「建成之后长什么样」。** 全文讲怎么建，没讲建完之后用起来是什么体验。给决策者看的文档，这一段往往比架构图更有说服力。

### 审阅时的输出格式

```
整体判断（一两句）

## P0 · 事实错误
**① <一句话标题>**
<问题是什么，证据在哪（章节号 / 文件行号），正确的应该是什么>

## P1 · 前后不一致
<表格：位置 | 问题>

## P2 · 影响评审效果
<同上>
```

每条都要能指到具体位置。「建议精简」这种没有位置的意见没有价值。

## 5. 精简的判断标准

用户说「太啰嗦」时，按这个顺序砍：

1. **与其他章节重复的内容** —— 砍掉，留交叉引用
2. **长段论述** —— 转成表格，通常能省一半
3. **实施细节**（完整配置、命令、查询语句）—— 移附录
4. **铺垫词和连接词** —— 直接删
5. **举例** —— 保留一个最有代表性的，删其余

**不要砍**：具体数字、出处引用、⚠ 风险提示、「未验证」标注。这些是文档可信度的来源，砍了就只剩观点。
